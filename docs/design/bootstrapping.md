# Bootstrapping — the foundational state

Status: design v1 (task 0008). Question: what exists *before the first act* —
and what does producing that state require?

## 1. The customary constitution

At genesis there is no enacted law. The corpus is (nearly) empty; the
cities already live by **custom**. The bootstrap problem is therefore not
"how do we create a legal order" but "how do we record the one that already
exists in the fiction". In-fiction, the answer is known: the Concord of the
Nine Cities did not create these customs — it **recognized** them. The
foundational state is the written record of that recognition.

Authorship: the seed is written by the *story designer* (the operator),
exactly as the world registry is generated by `world genesis`. It is
authored data, not generated data — generation comes later, when the
director starts synthesizing events *on top of* the seed.

## 2. What the foundational state contains

| component | status before this task | where it lives |
|---|---|---|
| civil registry (cities, persons, offices) | exists | `data/world/world.json` (genesis) |
| jurisdictions, ontology, paradigms | exists | `data/world/legal/` |
| concrete resources (24) | exists | `data/world/legal/resources/` |
| **norms — customary rules in force** | partial (4 of 15) | `data/world/legal/norms/` |
| **holdings — standing legal facts** | missing | same documents as norms (new) |
| **the founding corpus** (git-side seed) | ad hoc (e2e only) | the archive's first commit |
| pending matters | empty by definition | `matters.json` |

Two gaps: **holdings** (no data yet) and the **founding corpus** (only ever
created inside the e2e test). And the norms seed must cover all fifteen
jurisdictions minimally.

## 3. The seed format: situation documents

One YAML document per jurisdiction holds its *situation at genesis* —
norms **and holdings together**, because holdings cite the norms they exist
under (`under: N-0001`) and must never drift apart:

```yaml
jurisdiction: fisheries
norms:
  - id: N-0001
    rule_form: open_access
    object: {kind: northern_banks, type: resource}
    aspect: access_right
    subjects: []
    beneficiaries: [fisher]
    source: custom
    status: in_force
holdings:
  - id: H-0001
    holder: {city: cogswich, actor_kind: fisher}
    object: {kind: northern_banks, type: resource}
    activity: fish
    under: N-0001
```

A `holder` is a structured party: `{city: <slug>?, actor_kind: <kind>?}` —
either or both ("the fishers of Cogswich", "Brasshaven", "any carrier").
This deliberately covers all three holding shapes from the 0009 taxonomy
(resource use, statuses, rights/relationships) without new concepts.

The **snapshot principle applies**: the seed is simply the *first*
situation document. A simulation bootstraps by loading these documents;
evolution saves new ones; any saved document — seed or snapshot — is a
valid bootstrap point for a later run.

## 4. The founding corpus (git-side seed)

The archive itself needs an initial commit, so that `main` exists and the
corpus layout is in place before the first bill:

- `constitution/01-foundation.md` — the Concord's founding text: the
  cities, the common law, the recognition of custom (short, authored);
- the six domain directories and `municipal/<city>/` placeholders as the
  corpus grows into them.

One commit — "The Founding Corpus" — authored by the Keeper. This is what
the e2e currently does ad hoc; bootstrap makes it a first-class,
repeatable act. (Idempotency: bootstrap refuses to re-found a non-empty
archive unless forced.)

## 5. The bootstrap process

```
1. polis world genesis            # the civil registry (exists)
2. legal seed validation          # jurisdictions, resources, norms, holdings
                                  #   cross-checked as one consistent state
3. founding corpus commit         # constitution + layout, by the Keeper
4. situation documents load       # the run's working state = the seed
5. empty matters store            # institutional time starts at zero
```

Step 2 must pass before anything proceeds — bootstrapping an inconsistent
world poisons every later replay. The validator checks: every norm's
rule_form/object/aspect against its jurisdiction and resources; every
holding's `under` against an existing norm, its activity against the
jurisdiction's activities, its holder against the world registry.

## 6. How the state evolves afterwards

Already specified in `norms-generalization.md` §7 and implemented in
`norms.py`: enactment adds/flips norms (source custom → statute with
`source_ref`); amendment supersedes; repeal marks `repealed` and custom
revives by default. Holdings are re-pointed or become contested
(vested-rights disputes). Each ratified bill thus moves the situation; each
saved situation is a new bootstrap point.

## 7. Deliberately out of scope here

- *Why* events happen (activity signatures, 0012) and *what makes a
  dispute* (incompatibility, 0013) — these consume the seed, they are not
  part of it.
- Richer seeds (more norms, more holdings, narrative depth) — grow as
  stories demand; the schema won't change.

## 8. What this task delivers

1. Holdings: model + validation, folded into the situation documents.
2. Minimal norm seeds (+ at least one holding) for the remaining eleven
   jurisdictions, completing the fifteen.
3. A legal-seed validator (`polis world legal validate`) implementing step 2.
4. This document. The founding-corpus commit (step 3) becomes part of the
